Arquitectura general

Rails 8 promueve el paradigma de la aplicación web autosuficiente (One-person framework). Esto significa que no necesitamos montar servidores de Node.js, configuraciones complejas de Webpack ni bases de datos de Redis para colas y caché.

  • Propshaft se encarga de servir los archivos estáticos de forma liviana.
  • Tailwind CSS compila directamente mediante un binario independiente gracias a la gema tailwindcss-rails.
  • Pagy procesa la paginación con un consumo insignificante de memoria RAM y microsegundos de CPU.
  • Solid Suite (Cache, Queue, Cable) utiliza la propia base de datos relacional para gestionar tareas en segundo plano y WebSockets sin requerir software adicional.

Parte I · Fundamentos y Análisis del Sistema

Capítulo 1 — Presentación del proyecto y requerimientos

En la gestión cotidiana de un taller automotriz, el desorden operativo suele originarse en la falta de un registro centralizado de los clientes y sus respectivos vehículos. Frecuentemente, los datos de contacto y el historial de automóviles atendidos se encuentran dispersos en cuadernos o planillas no normalizadas.

El proyecto taller-mecanico se diseñó como una solución web integral y moderna construida con Ruby on Rails 8. El sistema resuelve el núcleo del problema registrando de forma relacional y estructurada los propietarios y sus autos, sirviendo de base sólida para el posterior seguimiento de órdenes de trabajo, repuestos y cobros.

1.1 Objetivos específicos del software

  • Registro unificado de clientes: Almacenamiento seguro de nombre, apellido, teléfono y estado activo del cliente.
  • Gestión del parque automotor: Asociación directa de cada vehículo con su titular, guardando marca, modelo, año de fabricación, matrícula (patente) y color.
  • Búsqueda en tiempo real: Localización veloz de clientes por coincidencias parciales de nombre, apellido o número de teléfono.
  • Panel de control intuitivo: Dashboard principal con métricas resumidas en tarjetas (KPIs) y accesos rápidos a las operaciones comunes.
  • Navegación moderna y responsiva: Barra lateral (sidebar) colapsable con soporte completo para dispositivos móviles y escritorio.
CONCEPTO: CONVENTION OVER CONFIGURATION (CoC)

Ruby on Rails se rige por el principio de "Convención sobre Configuración". Esto significa que si seguimos los estándares de nombres predeterminados de Rails (por ejemplo, clase en singular como Customer y tabla en plural en la base de datos como customers), el framework resuelve automáticamente las relaciones, consultas SQL y enlaces sin necesidad de escribir extensos archivos de configuración XML o JSON.

Capítulo 2 — Análisis funcional y casos de uso

El sistema cuenta con flujos de trabajo claros orientados a recepcionistas y administradores del taller. Analicemos los casos de uso principales:

2.1 Caso de Uso 1: Registro y Gestión de Clientes

  1. El recepcionista accede a la sección /clientes.
  2. Visualiza el listado de clientes paginado de 5 en 5 (gracias al motor Pagy).
  3. Puede filtrar la lista escribiendo cualquier término en la barra de búsqueda; la consulta se ejecuta con coincidencias insensibles a mayúsculas/minúsculas.
  4. Al pulsar "Nuevo Cliente", completa el formulario con nombre, apellido y teléfono.
  5. Al pulsar "Guardar", el sistema valida la entrada y redirige al listado general.
  6. Al entrar a editar un cliente, el sistema despliega el formulario y además una tabla integrada con todos los vehículos que posee dicho cliente, con enlaces directos para registrar nuevos autos asociados a él.

2.2 Caso de Uso 2: Gestión de Vehículos (Autos)

  1. Desde el panel lateral o desde la ficha de un cliente, se accede a /cars.
  2. El listado presenta marca, modelo, año, patente, color (mostrado con un badge visual estilizado) y el nombre completo del cliente propietario.
  3. Al crear un nuevo auto, se selecciona el cliente correspondiente de una lista desplegable ordenada alfabéticamente. Si se accedió desde la ficha de un cliente específico, el selector viene precargado automáticamente.
¿POR QUÉ BORRADO EN CASCADA (DEPENDENT: :DESTROY)?

En el modelo de datos, un automóvil no puede existir en el taller sin un cliente titular responsable. Si un cliente fuese eliminado del sistema y sus autos quedasen huérfanos, la base de datos sufriría una inconsistencia referencial. Por este motivo, la asociación en Rails se define como has_many :cars, dependent: :destroy y en PostgreSQL se refuerza con una clave foránea (foreign_key).

INSPECCIÓN PROFUNDA: POSTGRESQL VS SQLITE

Mientras que SQLite es ideal para prototipado rápido, entornos de desarrollo locales simples o aplicaciones de un solo archivo, PostgreSQL es el motor relacional estándar de facto en producción para sistemas empresariales:

  • Concurrencia real: Permite lecturas y escrituras simultáneas multi-hilo y multi-proceso sin bloqueos a nivel de archivo (evitando el error database is locked).
  • Índices avanzados y tipos de datos: Soporta tipos nativos como JSONB, UUID, arreglos y búsquedas por expresiones con índices funcionales.
  • Integridad estricta: Chequeo exhaustivo y transaccional de restricciones de claves foráneas y tipos de datos.

Parte II · Entorno de Desarrollo y Creación

Capítulo 4 — Ruby esencial para desarrolladores Rails

Ruby on Rails no es un lenguaje nuevo; es una librería (gem) escrita en Ruby. Para entender el código de este taller mecánico, es vital dominar las estructuras idiomáticas que Rails utiliza permanentemente.

4.1 Símbolos vs Strings

En Ruby, un String es mutable y genera una nueva asignación de memoria cada vez que se declara. Un Symbol (inicia con dos puntos, ej. :first_name, :destroy) es inmutable y único en el entorno de ejecución, lo que lo hace perfecto como identificador de claves en hashes y parámetros: 

# Strings (objetos distintos en memoria)
"nombre".object_id != "nombre".object_id # true

# Símbolos (mismo objeto en memoria para toda la vida del proceso)
:nombre.object_id == :nombre.object_id   # true

4.2 Hashes con sintaxis moderna

Cuando la clave de un hash es un símbolo, Ruby permite omitir la flecha hashrocket (=>) usando los dos puntos a la derecha: 

# Sintaxis antigua:
cliente = { :first_name => "Carlos", :phone => "11223344" }

# Sintaxis idiomática moderna (usada en Rails):
cliente = { first_name: "Carlos", phone: "11223344" }

4.3 Bloques, Lambdas y Scopes

Un bloque es una porción de código delimitada por do ... end o llaves { ... }. En el modelo Customer de este proyecto encontramos una expresión lambda (-> { ... }) para ordenar: 

scope :ordered, -> { order(Arel.sql("LOWER(last_name)"), Arel.sql("LOWER(first_name)")) }

La flecha -> crea un bloque ejecutable que Active Record evalúa cada vez que se llama al método Customer.ordered, garantizando que el ordenamiento se resuelva de forma dinámica.

4.4 Métodos con signos de exclamación e interrogación

  • Predicados (?): Métodos que retornan un booleano (true o false), por ejemplo params[:q].present? o current_page?(path).
  • Mutantes o peligrosos (!): Métodos que lanzan una excepción si fallan, por ejemplo @car.destroy! en CarsController. Si la eliminación fallara por una restricción de base de datos, Rails detendrá la ejecución lanzando un error en lugar de retornar silenciosamente false.

Para ejecutar y desarrollar este proyecto en Windows, Linux o macOS, requerimos una configuración de entorno consistente.

CLAVES FORÁNEAS EN POSTGRESQL

El campo customer_id en la tabla cars almacena el número de id del cliente titular. En PostgreSQL, esta relación está blindada con una restricción formal (FOREIGN KEY (customer_id) REFERENCES customers(id)). Esto impide que se pueda insertar un auto con un customer_id que no exista en la tabla de clientes.

class AddCustomerToCars < ActiveRecord::Migration[8.1]
  def change
    add_reference :cars, :customer, null: false, foreign_key: true
  end
end
¿QUÉ HACE ESTA MIGRACIÓN EN POSTGRESQL?
  1. Crea la columna customer_id BIGINT NOT NULL en la tabla cars.
  2. Crea un índice de búsqueda en Postgres: CREATE INDEX index_cars_on_customer_id ON cars (customer_id);.
  3. Añade la restricción de integridad referencial: ALTER TABLE cars ADD CONSTRAINT fk_rails_... FOREIGN KEY (customer_id) REFERENCES customers (id);.

Capítulo 9 — Active Record en profundidad: consultas y scopes

Active Record es el motor ORM (Object-Relational Mapping) de Rails. Su función es traducir tablas de bases de datos a clases de Ruby, filas a objetos e instrucciones de persistencia a sentencias SQL seguras contra inyecciones maliciosas.

9.1 Scopes personalizados y Arel SQL

En el modelo Customer, el listado debe mostrarse alfabéticamente por apellido y nombre, sin que las mayúsculas interfieran en el orden (en ASCII, una 'Z' mayúscula va antes que una 'a' minúscula). 

scope :ordered, -> { order(Arel.sql("LOWER(last_name)"), Arel.sql("LOWER(first_name)")) }
¿POR QUÉ SE USA Arel.sql?

Rails 6, 7 y 8 protegen las consultas bloqueando fragmentos de texto crudo en métodos como order si detectan riesgo de inyección SQL. Al envolver la función SQL nativa con Arel.sql("LOWER(...)"), le indicamos explícitamente a Rails que se trata de una instrucción SQL segura y sanitizada por el programador.

9.2 Consultas con parámetros con nombre (Named Binds)

En el controlador CustomersController, la búsqueda por texto se implementa con interpolación segura: 

criterio = "%#{params[:q]}%".downcase
@customers = Customer.where(
  "lower(first_name) LIKE :q OR lower(last_name) LIKE :q OR lower(phone) LIKE :q",
  q: criterio
)

El uso de :q evita que un atacante cierre comillas para inyectar código malicioso (SQL Injection), ya que el adaptador de PostgreSQL parametriza el valor antes de enviarlo al servidor de base de datos.

Capítulo 10 — Modelos del sistema: Customer y Car (relación 1:N)

Analicemos el código fuente exacto de los dos modelos nucleares del taller mecánico.

10.1 Modelo Customer (app/models/customer.rb)

class Customer < ApplicationRecord
  has_many :cars, dependent: :destroy

  scope :ordered, -> { order(Arel.sql("LOWER(last_name)"), Arel.sql("LOWER(first_name)")) }

  def full_name
    [ first_name, last_name ].compact_blank.join(" ")
  end
end
ANÁLISIS DEL MÉTODO full_name

El método full_name aprovecha el método de Ruby compact_blank (incorporado en Active Support). Si last_name o first_name estuviesen en blanco o fuesen nil, no se generan dobles espacios indeseados al invocar join(" ").

10.2 Modelo Car (app/models/car.rb)

class Car < ApplicationRecord
  belongs_to :customer
end

auto = c.cars.create(brand: "Toyota", model: "Yaris", year: 2022, plate: "AE123CD", color: "Gris")

# 3. Comprobar la relación bidireccional
auto.customer.full_name # => "María González"
c.cars.count            # => 1

# 4. Probar el borrado en cascada
c.destroy

Parte IV · Rutas y Controladores

Capítulo 11 — Sistema de enrutamiento: DSL y convenciones REST

El archivo config/routes.rb define el mapa de navegación de la aplicación web, asociando una solicitud HTTP entrante (Verbo + URI) con el controlador y método correspondiente.

11.1 Código fuente de config/routes.rb

Rails.application.routes.draw do
  resources :cars, except: :show

  # Health check para monitoreo y despliegue
  get "up" => "rails/health#show", as: :rails_health_check

  # Ruta raíz del sistema
  root "home#index"

  # Rutas hispanizadas para Clientes
  get "clientes", to: "customers#index", as: :clientes
  get "clientes/new", to: "customers#new", as: :new_cliente
  post "clientes", to: "customers#create"
  get "clientes/:id/edit", to: "customers#edit", as: :edit_cliente
  patch "clientes/:id", to: "customers#update", as: :cliente
  delete "clientes/:id", to: "customers#destroy"
end
RECURSOS REST AUTOMÁTICOS VS RUTAS INDIVIDUALES

Para la entidad cars se utiliza la macro REST: resources :cars, except: :show. Esta sola línea genera automáticamente las 6 rutas estándar (index, new, create, edit, update, destroy), excluyendo show porque el diseño del taller no requiere una página individual para cada auto, sino que los gestiona directamente desde la tabla de autos y la ficha del cliente.

Para los clientes, se declararon rutas manuales en español (/clientes) mapeándolas al controlador en inglés CustomersController, creando los helpers de URL clientes_path, new_cliente_path y edit_cliente_path.

Capítulo 12 — Controladores: flujo de acciones y parámetros seguros

Los controladores heredan de ApplicationController y actúan como intermediarios: extraen datos de la solicitud HTTP, invocan operaciones en los modelos y seleccionan la vista a renderizar.

12.1 Controlador CustomersController

class CustomersController < ApplicationController
  def index
    if params[:q].present?
      criterio = "%#{params[:q]}%".downcase
      @customers = Customer.where(
        "lower(first_name) LIKE :q OR lower(last_name) LIKE :q OR lower(phone) LIKE :q",
        q: criterio
      )
    else
      @pagy, @customers = pagy(:offset, Customer.ordered.order(:id))
    end
  end

  def new
    @customer = Customer.new
  end

  def create
    @customer = Customer.new(customer_params)
    @customer.save
    redirect_to clientes_path
  end

  def edit
    @customer = Customer.includes(:cars).find(params[:id])
  end

  def update
    @customer = Customer.find(params[:id])
    @customer.update(customer_params)
    redirect_to clientes_path
  end

  def destroy
    @customer = Customer.find(params[:id])
    @customer.destroy
    redirect_to clientes_path
  end

  private

  def customer_params
    params.require(:customer).permit(:first_name, :last_name, :phone)
  end
end
OPTIMIZACIÓN N+1 CON includes(:cars)

En la acción edit, se ejecuta: Customer.includes(:cars).find(params[:id]).
Al usar includes(:cars), Active Record carga en una sola consulta adicional todos los automóviles de ese cliente. Cuando la vista edit.html.erb itera sobre @customer.cars, no efectúa nuevas consultas a PostgreSQL, previniendo el temido problema de rendimiento N+1 queries.

12.2 Controlador CarsController y la novedad de Rails 8: params.expect

class CarsController < ApplicationController
  before_action :set_car, only: %i[ edit update destroy ]
  before_action :load_customers_for_form, only: %i[ new create edit update ]

  def index
    @cars = Car.includes(:customer).order(:brand, :model)
  end

  def new
    @car = Car.new(customer_id: params[:customer_id])
  end

  def edit
  end

  def create
    @car = Car.new(car_params)

    if @car.save
      redirect_to cars_path, notice: "Auto guardado correctamente."
    else
      render :new, status: :unprocessable_content
    end
  end

  def update
    if @car.update(car_params)
      redirect_to cars_path, notice: "Auto actualizado correctamente."
    else
      render :edit, status: :unprocessable_content
    end
  end

  def destroy
    @car.destroy!
    redirect_to cars_path, notice: "Auto eliminado.", status: :see_other
  end

  private

  def set_car
    @car = Car.find(params.expect(:id))
  end

  def car_params
    params.expect(car: [ :brand, :model, :year, :plate, :color, :customer_id ])
  end

  def load_customers_for_form
    @customers = Customer.ordered
  end
end
NOVEDAD DE RAILS 8: params.expect

En versiones previas de Rails, los Strong Parameters se definían como params.require(:car).permit(...) y para parámetros individuales se usaba params[:id]. Si el parámetro requerido no estaba presente, params.require lanzaba un error ActionController::ParameterMissing que debía capturarse.
Rails 8 introduce la directiva params.expect(...), mucho más concisa y estricta, que valida tanto parámetros individuales obligatorios (params.expect(:id)) como estructuras completas de hashes y listas blancas.

Capítulo 15 — Hotwire: Aceleración con Turbo y Stimulus JS

Hotwire (HTML Over The Wire) es la filosofía de Rails para crear aplicaciones reactivas y modernas enviando HTML directamente desde el servidor en lugar de complejas APIs de JSON consumidas por frameworks pesados.

15.1 Turbo Drive

Está activo por defecto mediante la gema turbo-rails. Cada vez que el usuario hace clic en un enlace o envía un formulario, Turbo intercepta la petición, la ejecuta mediante fetch en segundo plano y reemplaza el contenido del <body> sin recargar los recursos estáticos (CSS/JS) en el navegador. Esto otorga la velocidad y fluidez de una Single Page Application (SPA).

15.2 Stimulus JS: Controlador del Sidebar

Para elementos que sí requieren lógica en el cliente (como abrir y cerrar el menú lateral en dispositivos móviles), se utiliza Stimulus. El código se encuentra en app/javascript/controllers/sidebar_controller.js: 

import { Controller } from "@hotwired/stimulus"

export default class extends Controller {
  static targets = [ "panel", "opener", "content" ]

  toggle() {
    this.panelTarget.classList.toggle("-translate-x-full")
    this.openerTarget.classList.toggle("hidden")
    this.contentTarget.classList.toggle("ml-0")
    this.contentTarget.classList.toggle("ml-56")
  }
}
CÓMO VINCULA STIMULUS EL HTML CON JAVASCRIPT
  1. En application.html.erb, el <body> declara: data-controller="sidebar".
  2. El panel lateral declara: data-sidebar-target="panel".
  3. El botón para colapsar declara: data-action="click->sidebar#toggle".
  4. Al hacer clic, Stimulus ejecuta el método toggle(), alternando las clases de Tailwind sin necesidad de escribir selectores manuales con document.querySelector.

Capítulo 16 — Paginación de alto rendimiento con Pagy

Cuando el taller almacena cientos o miles de clientes, renderizar toda la lista en una sola pantalla colapsaría el rendimiento de la red y el navegador. Para solucionar esto se integró la gema Pagy.

16.1 Configuración en config/initializers/pagy.rb

Pagy.options[:limit] = 5

Esta directiva establece que por defecto cada página mostrará únicamente 5 registros a la vez.

16.2 Uso en el Controlador y Vista

# En CustomersController#index:
@pagy, @customers = pagy(:offset, Customer.ordered.order(:id))

En la vista app/views/customers/index.html.erb se renderiza la barra de navegación:

<!-- Muestra: Página 1 de 4, botones anterior y siguiente -->
<%= raw pagy_nav(@pagy) if @pagy.pages > 1 %>
¿POR QUÉ PAGY EN VEZ DE KAMINARI O WILL_PAGINATE?

Pagy fue escrita desde cero con obsesión por la velocidad: consume hasta 30 veces menos memoria y es hasta 40 veces más rápida que alternativas históricas como Kaminari, sin sobrecargar los objetos de Active Record con métodos innecesarios.

Parte VI · Avanzado, Práctica y Reconstrucción

Capítulo 17 — Buenas prácticas, seguridad y validaciones

A partir de la auditoría técnica realizada, identificamos áreas clave para fortalecer la robustez del sistema en un entorno de producción.

17.1 Incorporación de Validaciones de Modelo

Actualmente los modelos Customer y Car delegan parte de la integridad a la base de datos. Para ofrecer una experiencia de usuario superior con mensajes de error descriptivos en los formularios, se recomienda añadir validaciones a nivel de modelo: 

# app/models/customer.rb
class Customer < ApplicationRecord
  has_many :cars, dependent: :destroy

  validates :first_name, :last_name, presence: true, length: { maximum: 60 }
  validates :phone, presence: true, format: { with: /\A[0-9\-+\s()]+\z/, message: "solo permite números y guiones" }

  scope :ordered, -> { order(Arel.sql("LOWER(last_name)"), Arel.sql("LOWER(first_name)")) }
  # ...
end

# app/models/car.rb
class Car < ApplicationRecord
  belongs_to :customer

  validates :brand, :model, presence: true
  validates :plate, presence: true, uniqueness: { case_sensitive: false }
  validates :year, numericality: { only_integer: true, greater_than: 1950, less_than_or_equal_to: -> { Time.current.year + 1 } }
end

17.2 Manejo de Errores en Controladores

En CustomersController#create y #update, es una buena práctica evaluar el éxito de la operación para renderizar nuevamente el formulario con el código de estado HTTP 422 Unprocessable Entity si alguna validación no se cumple: 

def create
  @customer = Customer.new(customer_params)
  if @customer.save
    redirect_to clientes_path, notice: "Cliente registrado con éxito."
  else
    render :new, status: :unprocessable_entity
  end
end

Capítulo 20 — Guía de reconstrucción del sistema desde cero

Si necesitas replicar exactamente este sistema en otra máquina o proyecto universitario, sigue esta secuencia cronológica de comandos y pasos:

  1. Crear el proyecto con PostgreSQL y Tailwind: 
    rails new taller-mecanico -d postgresql --css tailwind
cd taller-mecanico
  2. Agregar gemas al Gemfile: 
    bundle add pagy
  3. Configurar inicializador de Pagy en config/initializers/pagy.rb: 
    Pagy.options[:limit] = 5
  4. Generar migraciones y modelos: 
    bin/rails generate model Customer first_name:string last_name:string phone:string active:boolean
bin/rails generate model Car customer:references brand:string model:string year:integer plate:string color:string
bin/rails db:create
bin/rails db:migrate
  5. Definir asociaciones y scopes:

    Configurar has_many :cars, dependent: :destroy en Customer y belongs_to :customer en Car.

  6. Generar controladores: 
    bin/rails generate controller Home index
bin/rails generate controller Customers
bin/rails generate controller Cars
  7. Configurar rutas en config/routes.rb vinculando el Dashboard como root y los recursos de cars y clientes.
  8. Levantar el entorno de desarrollo: 
    bin/dev

    Acceder a http://localhost:3000 en el navegador.
